## 设计 ② v2：收编归属——元数据主轴，行为推断降级

### v1 被驳回的核心

「回溯回填 ≥1 条成功 = 同一份宿主日志 = 归属正确」**不成立**：宿主表面是共享的，
任何在根目录启动的会话都读得到它。回填成功只证明「我能看见这段日志」。
行为推断（事件数、回填）永远是替代品，替代品在边界情况必错。

### v2 机制：读产生者元数据，行为信号只做旁证

**主判据（元数据，本体）**：归属判定的输入不是「这个会话做了什么」，而是
「这段历史是谁写的」。宿主日志里存着产生者元数据——写这些旧事件的 sessionId、
cwd、创建者标记——只是现在没人去读。收编动作改为：

```
1. 从根账本最老的宿主区间对应的宿主日志段，读产生者元数据
   （写事件的 sessionId / cwd / 创建者标记——具体字段需宿主侧确认，见「待确认」）
2. 元数据指向的 sessionId = 归属者：
   - 该会话现在活跃 → 正式收编（owner.json 照旧写）
   - 该会话不存在（宿主已新开 sessionId）→ 根目录挂「归档」态（见下）
3. 元数据读不到（旧格式/字段缺失）→ 挂「候选」只读态，等待元数据可读或人工裁决
```

**辅助信号（旁证，不再做主判据）**：
- 持续 turn/end（外部有人驱动）——比事件计数强（v1 的 N=5 一个干活 subagent 一趟
  就够，驳回），但仍是行为推断，只用于「候选态过期后的处置选择」，不用于归属证明。
- 启动回溯回填——保持现有功能不动，但**从归属判据中除名**。

### 归档态：显式挂起，可逆（复审要求写清）

归档不是判决，是「归属未决」的显式记录：

```
归档态 = owner.json 写 { status: "archived", reason, at }（而非收敛到某个 sid）
可逆路径：任何时候出现会话能证明「这段历史是我产生的」（元数据匹配其 sessionId），
  → 翻转：owner.json 改写为正常收编（sid = 该会话），归档态作废
  → 翻转动作本身也是一次 owner.json 原子写，与现机制同原语
无人认领：归档态长期保持（只读挂载对所有人开放），不自动收敛到任何会话
```

### 待确认（宿主侧）

1. 宿主日志的产生者元数据字段名与读取路径（sessionId/cwd/创建者标记）——
   这决定主判据能否落地；若宿主日志不携带，需宿主协同（与摘要模板注入口同一张协同清单）。
2. 新旧 sessionId 的映射关系（宿主重启后 sessionId 是否延续语义）。

### 与现实现的兼容

- 有 owner.json 的存量部署：机制不激活（已归属的照旧）。
- ownerCorrupt：仍拒绝收编（v0.7.9 行为不变）。
- 候选/归档态下：读类工具全可用，写路径走各自 sessions/<sid>/——与 phase1 只读闸门同款。
